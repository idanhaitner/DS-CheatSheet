7.1 Amortized Analysis

Average cost per operation over a worst-case sequence: not a probabilistic average. If any sequence of \(n\) ops takes \(T(n)\) worst-case, the amortized cost per op is \(T(n)/n\). The course teaches two methods (the potential method is not in the lectures):

MethodIdeaExample
AggregateTotal cost of n ops is \(T(n)\); amortized = \(T(n)/n\).Dynamic array (doubling): n insertions copy at most n + n/2 + n/4 + … < 2n elements total → \(T(n)=O(n)\) ⟹ O(1) amortized per insert.
AccountingAssign each op a charge \(\hat c_i\); cheap ops overpay to bank credit stored on objects. Invariant (know the formal version!): for every prefix \(j\): \(\sum_{i=1}^{j} c_i \le \sum_{i=1}^{j} \hat c_i\) — the bank never goes negative at any point, not just at the end.Same dynamic array: charge 3 coins per insert: 1 pays the insert, 2 go to the bank. When the array doubles (cost n), pay from the bank (each of the n/2 elements since last resize saved 2 coins). Bank never goes negative ⟹ O(1) amortized.

Binary counter — the full worked example

Counter stored in bit array \(A[0..k{-}1]\) (\(A[0]\) = LSB), starting at all zeros. Cost = number of bit flips.

Increment(A) 
Increment(A):
    i ← 0
    while i < k and A[i] = 1:
        A[i] ← 0                // flip trailing 1s to 0
        i ← i + 1
    if i < k: A[i] ← 1          // first 0 becomes 1

Worst case of a single Increment: \(\Theta(k)\) flips (e.g. \(0111\ldots1 \to 1000\ldots0\)). But amortized it's O(1), two ways:

AggregateAccounting
Bit \(i\) flips once every \(2^i\) increments ⟹ at most \(\lfloor n/2^i\rfloor\) flips in \(n\) increments. Total flips \(< \sum_{i=0}^{\infty} n/2^i = 2n\) ⟹ \(T(n)=\Theta(n)\) ⟹ O(1) amortized. Charge $2 per Increment. Credit invariant: every bit that equals 1 stores $1. The 1→0 flips are paid by the credits sitting on those bits; $1 of the charge pays the single 0→1 flip; the remaining $1 is stored on the new 1. Invariant holds ⟹ O(1) amortized.
Exam form: "state the credit invariant and prove Increment is O(1) amortized" — the invariant sentence in bold is the answer they grade.

Stack with Multipop — accounting

\(\textsf{Multipop}(S,k)\): pop until empty or \(k\) elements popped. A single Multipop costs \(\Theta(n)\), but:

OpActual cost \(c_i\)Charge \(\hat c_i\)
Push12 ($1 pays the push, $1 stored on the element)
Pop / Multipop1 / #popped0 (paid by the $1 credit on each popped element)

Invariant: every stacked element holds $1. Total charge \(\le 2n\) ⟹ O(1) amortized. (Aggregate view: each element is pushed once and popped at most once ⟹ \(T(n)=O(n)\).)

Hash table rehashing — accounting ($3 trick)

Chaining, load factor \(\alpha=n/m\) kept in \([1/4,\,1]\): grow to \(2m\) when \(n=m\); shrink to \(m/2\) when \(n=m/4\). Rehash costs \(\Theta(m)\).

Insert charge = $3: $1 pays the insert, $2 stay in the table. After a grow-rehash the credit resets to 0; the next rehash happens only after \(m\) more inserts, which deposit \(2m\) dollars — enough to pay for moving all keys. ⟹ Insert is O(1) amortized (expected). Self-check from the slides: what is the minimal charge that still works for Delete with the shrink rule?

7.2 Union-Find (Disjoint Sets)

Maintains a partition into disjoint sets, each with a representative. Backbone of Kruskal's MST and connectivity queries.

OperationMeaning
MakeSet(x)new singleton set {x}
Find(x)return representative of x's set
Union(x,y)merge the two sets

Linked-list implementation + weighted union (lecture proof)

Each set = linked list + set object (head = representative, tail, size); every element points to its set object, so Find is \(\Theta(1)\). Union appends one list to the other and updates the set-pointers of every moved element.

Naive union is Θ(n) even amortized: MakeSet(1..n) then Union(2,1), Union(3,2), …, Union(n,n−1) appending the growing list each time updates \(2+3+\cdots+n=\Theta(n^2)\) pointers over \(2n{-}1\) ops. "Amortized" does not automatically mean fast.

Weighted-union heuristic: always append the smaller list to the larger one.

Theorem: any sequence of \(m\) ops with \(n\) MakeSets costs \(O(m + n\log n)\).

Proof (doubling argument): fix an element \(x\). Each time \(x\)'s set-pointer is updated, \(x\) was in the smaller list, so its new set is at least twice as large. Set sizes are \(\le n\), so \(x\)'s pointer is updated at most \(\log n\) times. Summing over all \(n\) elements: \(O(n\log n)\) pointer updates + \(O(m)\) for everything else. ∎

Forest implementation + two optimizations

  • Union by rank: attach the root of smaller rank under the root of larger rank; on a tie, pick either and increment the winner's rank.
  • Path compression: during Find, point every node on the path directly to the root.
Why "rank" and not "height"? (exam favorite) Path compression shortens paths, so the true height can silently decrease and cannot be maintained in O(1). Rank is only an upper bound on height: it never decreases, which is all union-by-rank needs.
Union by rank + path compression 
MakeSet(x): x.parent ← x;  x.rank ← 0

FindSet(x):
    if x.parent ≠ x:
        x.parent ← FindSet(x.parent)     // path compression
    return x.parent

Union(x, y):
    x ← FindSet(x);  y ← FindSet(y)
    if x.rank > y.rank:  y.parent ← x
    else:
        x.parent ← y
        if x.rank = y.rank:  y.rank ← y.rank + 1
ConfigurationCost of m operations
Linked list, naive unionO(m·n) worst (see pitfall above)
Linked list + weighted unionO(m + n log n)
Forest + union by rank onlyO(m log n) (height stays O(log n): a rank-h tree has ≥ 2^h nodes)
Rank + path compressionΘ(m·α(n)) ≈ O(m): α = inverse Ackermann, ≤ 4 for any realistic n (α(n)=4 already covers n up to ≫ 22048). A single op is still Θ(log n) worst-case.
Application: connected components: MakeSet each vertex, then for each edge (u,v) Union their sets. Two vertices are connected ⟺ same Find. Pitfall: the representative of a set can change after Union — never cache it across Unions.

7.3 Deamortization of rehashing

Problem: when a hash table grows, a normal rehash copies all \(n\) keys in one Insert → \(\Theta(n)\) spike. Deamortization spreads that copy over many Inserts so every Insert stays \(\Theta(1)\) worst-case.

Setup (chaining)

Table \(T\) has \(m\) cells \(T[0],\ldots,T[m-1]\). Each cell is the head of a linked list of keys that hashed there. There are \(n\) keys total; we keep \(n/m\in\Theta(1)\).

  • When \(n=m\): grow to size \(2m\) (copy every key into a new table).
  • When \(n=m/4\): shrink to \(m/2\) (slides focus on growing).

What a full rehash does

Copy from \(T\) (size \(m\)) into a new table \(T'\) (size \(2m\)) by walking every cell and every key:

Rehash — full copy 
(1) create T′ of size 2m
(2) for i = 0 to m−1
(3)     p ← T[i]              // open cell i
(4)     while p ≠ NULL
(5)         Insert(T′, p)     // copy this key
(6)         p ← p.next
Count the tiny steps in that loop. The lecture treats the copy as \(2m\) atomic actions (call them “copy steps”):
  • \(m\) cell opens: once per index, \(p\leftarrow T[i]\) (even if the list is empty).
  • \(m\) key copies: once per key, Insert(T′, key) then \(p\leftarrow p.next\).
Doing all \(2m\) of them inside one Insert costs \(\Theta(n)\). Deamortization does only a constant number of them per Insert.

Deamortized Insert

Keep two tables: live \(T\) (size \(m\)) and building \(T'\) (size \(2m\)). Remember where you paused in the copy: cell index \(i\) and list pointer \(p\).

Define one helper that does exactly one tiny action from the rehash loop:

CopyOneStep — open a cell OR copy one key 
CopyOneStep():
    if p = NULL:                 // finished the current list
        p ← T[i]                  // open the next cell
        i ← i + 1
    else:
        Insert(T′, p)             // copy this one key into T′
        p ← p.next

Then Insert only calls that helper a constant number of times:

Insert(x) 
Insert(x):
    insert x into T

    if h(x) ≥ i:                 // scan has not reached x’s cell yet
        call CopyOneStep() 4 times
    else:                       // scan already passed x’s cell
        insert x into T′ as well  // otherwise T′ would miss x
        call CopyOneStep() 3 times

    if |T| = m:                  // copy finished; switch tables
        T ← T′
        T′ ← new empty table of size 4m   (smart array → Θ(1))
Example (\(m=4\), keys \(1,8\) in \(T\), Insert(4)). After putting 4 into \(T\), the four CopyOneStep calls might be:
  1. \(p\leftarrow T[0]\) (open cell 0 → list \(1\to 8\))
  2. Insert(T′, 1); \(p\leftarrow\) next
  3. Insert(T′, 8); \(p\leftarrow\) NULL
  4. \(p\leftarrow T[1]\) (open cell 1, empty)
Stop. Next Insert continues from cell 2.
Why every Insert is \(\Theta(1)\)
Put \(x\) in \(T\) (and maybe \(T'\))\(\Theta(1)\)
At most 4 calls to CopyOneStep\(\Theta(1)\)
When \(n=m\): swap + smart-array allocate\(\Theta(1)\)

Why 4? Total copy work \(2m\) steps / \(m/2\) Inserts = 4 steps per Insert.

Smart array: allocating size \(4m\) without zeroing every cell costs \(\Theta(1)\) in the course model.

7.4 B-Tree Amortized Analysis

For a B-tree with 2-pass insertion/deletion, split/merge/shift operations can be charged to individual inserts/deletes.

Theorem

Starting from an empty tree, in any sequence of \(m\) insertions and deletions, the number of merge, split, and shift operations is at most \(\frac{3}{2}m\).

Accounting method

  • Cost of each merge / split / shift = 1.
  • Charge per insert or delete = \(3/2\).

Invariant (dollar storage on nodes):

  • Non-root node with \(t-1\) keys stores \(1/2\) dollar.
  • Node with \(2t-1\) keys stores \(3/2\) dollars.

Insertion: when node \(v_i\) splits (had \(2t-1\) keys), use its \(3/2\) dollars to pay for the split and put \(1/2\) on each child. If parent \(w\) reaches \(2t-1\) keys, take \(3/2\) from the operation's charge.

Deletion: when two siblings merge, use \(1/2\) dollar from each to pay the merge. Shifts funded from the \(3/2\) charge.

Amortized cost per insert/delete = O(1) for structural ops (tree height still \(O(\log n)\) per search). See B-trees for the structure itself.

7.5 BB[α] Trees (amortized rebuilding)

A different way to keep a BST balanced: instead of rotations, occasionally rebuild a whole subtree, and pay for it amortized. (Lecture 18 — never yet asked on an exam, prime Moed B material.)

Definition

\(\mathrm{size}(v)\) = number of vertices in \(v\)'s subtree. Vertex \(v\) has bounded balance \(\alpha\) if \(\ \mathrm{size}(v.\mathrm{left}) \ge \lfloor \alpha\cdot \mathrm{size}(v)\rfloor\ \) and \(\ \mathrm{size}(v.\mathrm{right}) \ge \lfloor \alpha\cdot \mathrm{size}(v)\rfloor\). A BB[α] tree (\(\alpha < 1/2\)) is a BST in which every vertex has bounded balance α. Height \(\le \log_{1/(1-\alpha)} n = O(\log n)\).

Insert / Delete

Do the plain BST insert/delete; then let \(w\) be the highest vertex that lost its balance, and rebuild \(w\)'s subtree into a perfectly balanced BST on the same keys. Worst case \(\Theta(n)\) (rebuilding the root), but rare — that's the point.

Amortized analysis (accounting, α = 1/3)

  • Charge per insert: \(4(\mathrm{height}+1) = O(\log n)\). Pay \(\mathrm{height}+1\) for walking down; leave $3 on every node along the insertion path.
  • Key lemma: when \(w\) (with \(M=\mathrm{size}(w)\)) goes out of balance, at least \(M/3\) inserts passed through \(w\) since the last rebuild involving it — each deposited $3 ⟹ \(w\) holds \(\ge M\) dollars, enough to pay the \(\Theta(M)\) rebuild.
  • Result: \(n\) inserts cost \(O(n\log n)\) total ⟹ O(log n) amortized per insert.
Why the lemma holds (α = 1/3): right after a rebuild \(w\) is perfectly balanced (each side ≈ \(M'/2\)); to reach the violating state \(\mathrm{size}(\mathrm{right}) = \lfloor M/3\rfloor - 1\) vs \(\mathrm{size}(\mathrm{left}) = M - \lfloor M/3\rfloor\), at least \(\tfrac13 M\) new keys must have been inserted into \(w\)'s subtree.
